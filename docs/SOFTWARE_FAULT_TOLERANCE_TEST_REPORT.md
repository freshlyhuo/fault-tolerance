# 软件容错测试报告

## 1. 测试概述

本报告用于验证基于 VSOA 发布订阅的硬件遥测、健康监测、故障诊断和故障恢复闭环能力。测试方案覆盖供电、热控、通信、姿轨控、动量轮等不同硬件故障类型；当前实测记录为供电子系统电压异常场景，发布方模拟蓄电池电压和母线电压越限，订阅方接收硬件指标后生成告警，故障诊断模块输出故障码，故障恢复模块根据故障码处置程序映射下发修复指令。

报告编写日期：2026-05-19  
板端日志时间：2025-02-26 02:46:27，板端系统时间与报告日期不一致，不影响本次功能结论。

## 2. 测试方案

### 2.1 测试目标

本次测试目标如下：

| 类别 | 测试目标 |
| --- | --- |
| 场景覆盖 | 验证不同硬件类别的典型遥测异常场景能否触发预期告警、诊断和修复流程 |
| 功能 | 验证健康监测、故障诊断、故障码处置程序映射、修复容器调用的闭环功能 |
| 性能 | 统计故障检测准确率和端到端故障修复时间 |
| 可靠性 | 验证链路在连续指标发布、状态去重和修复容器响应场景下能否稳定执行 |
| 易用性 | 验证命令行参数、配置路径、控制台输出和辅助排障工具是否便于现场测试 |

### 2.2 测试范围

本次测试覆盖以下链路：

```text
硬件遥测发布 -> VSOA PubSub 订阅 -> 健康监测阈值判断 -> 告警发送 ->
故障诊断 -> 故障码处置程序映射 -> 故障恢复计划执行 -> 修复容器指令下发
```

本次测试不覆盖真实硬件故障消除后的物理效果验证，仅验证软件链路能否正确完成诊断和修复计划执行。

### 2.5 性能测试项

本报告中的性能指标主要关注故障检测准确率和故障修复时间。正式性能测试需增加打点，统一记录健康监测触发告警、诊断输出、恢复计划开始、恢复计划结束四个时间点。

| 编号 | 指标 | 定义 | 统计方法 | 目标值 |
| --- | --- | --- | --- | --- |
| P-001 | 故障检测准确率 | 诊断结果与预期故障树、故障码、故障原因匹配的比例 | `正确诊断次数 / 故障注入次数 * 100%` | 本轮目标 100% |
| P-002 | 故障检测时延 | 从健康监测触发告警到故障诊断结果输出的时间 | `T1 - T0` | 记录实测值 |
| P-003 | 恢复调度时延 | 从故障诊断结果输出到恢复计划开始执行的时间 | `T2 - T1` | 记录实测值 |
| P-004 | 恢复计划执行时间 | 从恢复计划开始执行到全部恢复计划执行完成的时间 | `T3 - T2` | 记录实测值 |
| P-005 | 端到端故障修复时间 | 从健康监测触发告警到故障恢复模块完成全部恢复计划的时间 | `T3 - T0` | 记录实测值 |

打点定义如下：

| 打点 | 位置 | 记录内容 | 用途 |
| --- | --- | --- | --- |
| T0 | 健康监测生成首条 `firing` 告警时 | `health_alert_ms`、`alert_id`、`fault_code`、`metric_value` | 故障被健康监测发现的时间 |
| T1 | 故障诊断模块输出诊断结果时 | `diagnosis_result_ms`、`diagnosis_id`、`fault_tree_id`、`fault_code` | 故障被诊断确认的时间 |
| T2 | 故障恢复模块开始执行恢复计划时 | `recovery_plan_start_ms`、`plan_id`、`trace_id` | 修复计划开始时间 |
| T3 | 故障恢复模块完成全部恢复计划时 | `recovery_plan_finish_ms`、`plan_id`、`status`、`error` | 修复计划完成时间 |

建议打点日志格式：

```text
[perf][health_alert] trace=<trace_id> t_ms=<T0> alert=<alert_id> fault=<fault_code>
[perf][diagnosis_result] trace=<trace_id> t_ms=<T1> tree=<fault_tree_id> fault=<fault_code>
[perf][recovery_plan_start] trace=<trace_id> t_ms=<T2> plan=<plan_id>
[perf][recovery_plan_finish] trace=<trace_id> t_ms=<T3> plan=<plan_id> status=<SUCCESS|FAILED|CANCELED>
```

P-005 为当前关注的故障修复时间口径，包含告警发送、故障诊断、恢复计划匹配、修复容器 RPC 调用和恢复计划全部指令执行时间。所有性能打点应使用同一进程内的单调时钟或统一毫秒时间戳，避免板端系统时间跳变影响统计。

## 5. 测试步骤

1. 启动硬件指标发布服务，按场景矩阵发布对应硬件异常数据。
2. 启动软件容错集成测试程序，订阅 `/hardware/metrics`。
3. 健康监测模块接收硬件指标并进行阈值判断。
4. 健康监测模块向故障诊断模块发送告警。
5. 故障诊断模块根据故障树输出诊断结果。
6. 故障恢复模块根据故障码处置程序映射选择恢复方案。
7. 故障恢复模块调用修复容器，下发对应恢复计划中的修复指令。
8. 检查诊断结果、恢复结果、性能指标和程序退出状态。

## 7. 已修复问题

| 问题 | 原因 | 修复结果 |
| --- | --- | --- |
| 修复容器返回 `empty response body` | Go VSOA 客户端完成调用后应读取 `completed.Reply`，原实现读取了传入的空 reply 对象 | 已修复，恢复链路可正常得到容器响应 |
| Python 修复容器响应格式兼容性不足 | Python VSOA 回复中 `param` 不应预先编码成 JSON 字符串 | 已调整为对象型 `param` |
| 控制台重复打印每条指标流水 | PubSub 客户端和业务 Dispatcher 都打印成功处理日志 | 已删除成功流水日志，仅保留连接、错误、告警、诊断和恢复结果 |
| 首次正常指标产生恢复告警 | 状态机将首次正常状态也作为状态变化发送 | 已调整为首次正常只记录状态，不发送 `resolved` |

## 8. 测试结论

本次软件容错集成测试通过。系统能够完成以下闭环：

1. 通过 VSOA PubSub 接收硬件遥测指标。
2. 对供电电压异常进行健康监测和告警生成。
3. 根据故障树输出 `YW-RG-ZD-3` 故障诊断结果。
4. 根据故障码处置程序映射选择 `RP-003`。
5. 通过修复容器成功下发 `K50032`。
6. 输出恢复成功结果并正常结束测试。

当前测试结论：供电电压异常场景的软件容错闭环功能满足预期。本轮故障检测准确率为 100%，端到端故障修复时间在当前秒级日志粒度下约为 0-1 s。完整多硬件场景和毫秒级性能统计按测试方案继续补充实测记录。
